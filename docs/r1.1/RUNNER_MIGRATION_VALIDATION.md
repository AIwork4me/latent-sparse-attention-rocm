Negative regression tests (`tests/test_r11_device_policy.py` + extended `tests/test_r11_ops_contracts.py`) pin every corruption class: missing/altered/extra `DeviceAllow` entries, mode tampering, `DevicePolicy` drift, and unit-vs-host GPU node incompatibility.

**Last-mile hardening (2026-11-08, review of `d1a1c3c`, amended after adversarial review):** three further corrections. **(a) errno, not strerror**: the negative control matched the *string* "permission denied", but on Linux **EPERM(1)="Operation not permitted"** is the cgroup device filter's signature while **EACCES(13)="Permission denied"** is DAC — string matching would (i) false-abort on a genuine in-sandbox filter denial and (ii) accept a plain DAC rejection as filter evidence. Replaced by `ops/device-open-probe.py` (`os.open()` + `OSError.errno`, machine-parseable `OPEN-OK`/`OPEN-ERR <errno> <ERRNAME>`), run **inside the transient context** for all allowlisted nodes and the negative control, and **outside any filter under `setpriv --reuid lsa-runner --init-groups`** to evidence the strong tier's DAC premise (premise requires **rc==0 AND OPEN-OK**). The **strong tier is MANDATORY**: the runner cannot start on weak-tier-only evidence — if no non-allowlisted DAC-permitted device node exists, §7b aborts and the runner stays offline. The strong PASS requires *DAC permits outside the filter* AND *EPERM inside it*; EACCES-in-sandbox, ENOENT, ENXIO and every other errno are distinguished and hard-abort. All probe stderr persists to `/tmp/lsa-open-probe-stderr.log` and every abort names it (diagnosable post-mortem); staged probe files are removed by an EXIT trap even on abort. **(b) Validate-before-start sequencing**: step 6 now only installs the unit and reloads the manager — the runner stays **offline and not enabled**; §7 validates everything (parity, device access, isolation, writability, Triton JIT in the service cgroup); step 8 runs `systemctl enable --now` and the one-Listener check **only after all checks pass** (§8 failures name that the unit stays enabled + how to disable). Any pre-start failure leaves the runner offline (recover: `--resume` or `rollback-runner.sh`; the never-enabled inactive unit is reboot-safe and rollback handles it). **(c) Parity robustness**: `device-policy-check.sh parity` tolerates systemd's **implicit `DeviceAllow=char-rtc r`** injection when (and only when) the unit file sets `ProtectClock=yes` (verified on systemd 255 across 6 units — unconditional tolerance would hide real drift); a closed/strict policy with an empty allowlist aborts on EITHER side. The `emit-entries` transcription is captured fail-closed (explicit exit-code check + non-empty guard — a bare `mapfile < <(…)` swallows parser failures and would silently rebuild the zero-device context). Regression tests: `tests/test_r11_device_open_probe.py` (9 functional cases incl. EACCES-as-non-root, ENOENT, errno vocabulary) + `tests/test_r11_device_policy.py` char-rtc tolerance/drift pair + updated static pins (start-after-validation incl. no-`systemctl start` anywhere, fail-closed capture, errno structure, strong-tier-required, stderr-log).

### Q2 — Do `ProtectHome=true`, the new HOME and the systemd device sandbox permit runner startup and GPU access?

**Two defects found in the R1 draft unit; corrected in `ops/github-runner-lsa.service`:**

1. **`ProtectHome=true` hides ALL of `/home` — including the new `/home/lsa-runner`.** With the draft unit, `$HOME` would be unwritable/invisible → Triton kernel cache (default `$HOME/.triton`), torch extension dir and every home-writing library fail exactly at first kernel compile. Fix: `Environment=HOME=/opt/actions-runner-lsa/home` (under `ReadWritePaths`) + explicit `TRITON_CACHE_DIR` + `PYTORCH_EXTENSIONS_DIR` (belt and braces).
2. **`DeviceAllow` without `DevicePolicy=closed` is inert for filtering** (default policy `auto` allows everything). Fix: `DevicePolicy=closed` + the three `DeviceAllow` entries (`/dev/kfd`, `/dev/dri/renderD128`, `/dev/dri/card1` rw) → a true minimal-GPU allowlist. GPU reachability itself is by `video,render` group membership on the device nodes (`0660 root:video|render`, re-verified), the same mechanism the interactive user uses — no other privilege needed.
3. Runner startup: install is relocatable (no `/home/amd` strings in `.settings/` or `env.sh`; `workFolder: _work` relative); `WorkingDirectory=/opt/actions-runner-lsa` + `ReadWritePaths` covers listener state; outbound HTTPS to the Actions service is unrestricted. Syntax of the R1 draft passed `systemd-analyze verify`; the three-line delta preserves syntax (re-verify at install time — script does).

### Q3 — Can copied registration files create duplicate listeners or conflicting identities?

**Yes, if misused — mitigated by design.** `.runner` encodes identity `agentName: lsa-rocm-gfx1151` (pool Default, workFolder `_work`); `.credentials*` authenticate that same identity. Two installs with one identity running concurrently = listener conflict/erratic job leasing. Controls:
- The old `~/actions-runner-lsa` stays **offline permanently** (it is already offline; nothing restarts it).
- After post-migration validation the owner **retires** it (`mv ~/actions-runner-lsa ~/actions-runner-lsa.retired-pre-migration` — in the script's handoff), making accidental double-listen impossible.
- Rollback rule (in `rollback-runner.sh`): legacy runner and migrated copy are **mutually exclusive** — stop one before starting the other.
- Credential file modes tightened in the copy: original `.credentials` was group-readable (`0664`); the migration `chmod 600` all three identity files.
- Same-identity relocation is exactly what makes the **intentionally-kept queued run `42381769814`** (A2) execute on the migrated runner with its label set `[self-hosted, linux, rocm, gfx1151]` intact.
